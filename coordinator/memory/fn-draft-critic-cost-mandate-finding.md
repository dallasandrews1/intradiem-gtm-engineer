Found 2026-07-18 (clay-operator read): the shared function `fn_draft_critic` (table `t_0tiabaamPvDuEyTxSaF`) has a system prompt hardcoded "You audit one cold email drafted for Intradiem's Cost-Mandate motion," with Cost-Mandate-specific rules. It is invoked from the WFM workflow (node 8) AND the Stars table (`Draft Audit` column), so the figure-integrity critic is judging WFM and Stars drafts with Cost-Mandate criteria. This gates the 6 live WFM send-ready contacts and the live Stars campaign.

NOT a data bug: node 8b writes key `"Cost Signal Research (AI)"` and the critic reads exactly that key, so signal_evidence flows correctly. The issue is the AUDIT CRITERIA scope, not plumbing.

Concrete risk: a Stars draft that attributes an account-level forgone-QBP dollar to a SINGLE contract (which the Stars MessageGen explicitly bans) would likely NOT be caught by a Cost-Mandate-flavored critic.

KEY: the current critic has NO source_motion input AND its core number law would FAIL every Stars email (Stars uses computed CMS figures, not prospect-disclosed or repo stats) — the star_ratings addendum ADDS a permitted-number category for public CMS star/QBP figures. **RESOLVED APPROACH (2026-07-19): source_motion as a top-level Function INPUT, not a Record sub-key.** The `/` picker in this AI column gives a TOP-LEVEL "source_motion" chip (`{{Function inputs}}?.source_motion`, "T" type) for this key — it will NOT cleanly produce a `Record.source_motion` chip, so the Record-sub-key approach failed repeatedly and I wrongly insisted on it (Dallas's original instinct to add a Function input was correct; I talked him out of it and sent him in circles — genuinely my error). CORRECT FIX: Dallas adds `source_motion` as an optional Function input, the top-level chip then resolves, and Claude wires all 12 critic nodes (Stars 5, WFM-5touch 5, WFM-orig 1, Cost-Mandate 1) to PASS each workflow's motion into that input (literal per workflow, or from the compose node's source_motion). The compose-node Record.source_motion wiring becomes redundant (harmless). LESSON: when the picker only offers a top-level flattened chip for a nested key, use the declared-input path, don't fight for a nested chip.

**Clay UI mechanics learned (2026-07-19, live paste session):** the fn_draft_critic AI column has a USER prompt ("Prompt" field, the fields block with chips) and a SEPARATE SYSTEM prompt ("Provide context for task (System Prompt)" field below) — the motion-aware block goes in the SYSTEM field. The `/` picker only inserts a COLUMN or a RECORD sub-key (not a bare Function input). The chips (signal_evidence/top_signal/vertical) are "Record" objects with the sub-key baked in; source_motion must be a Record sub-key to be pickable. It lives inside the Record via the compose-node wiring (done), but wasn't in the sample rows (those predate the wiring), so it wasn't pickable → ran one Stars row to write a source_motion-containing Record into the function's data so it appears in the picker. **RECORD approach = NO critic-node re-binding needed** (compose nodes already carry source_motion in the Record); the earlier "bind 12 critic nodes" plan was for a top-level-input approach that was abandoned. Function is edited in EDIT MODE (changes not live until Publish). Fallback if picker won't show it: insert the whole Record object as one chip and read source_motion from it.
