2026-07-27: `gate-integrity-fanout.js` (the new fan-out + adversarial-verify workflow, see [[graph-engineering-audit-jul27]] move 2) ran clean on its first live pass against real Clay rows, no synthetic `--input`, and found two confirmed customer-leak paths plus one secondary defect. Both leaks were independently re-verified by a second agent that re-pulled the same live data itself before being reported. Full raw report in the workflow's task output; this is the durable summary.

**CONFIRMED LEAK 1 — Stars, table `t_0thtm73HHxyiupTuepK` ("Contacts (Buying Committee)").** 3 of 5 outbound sync action columns (`f_0tin6dodVjMf49to5qF` Finance, `f_0tin6h6mCEdNjeHZ79x` Quality, `f_0tinhhiCbBMkHq7bm77` Ops) have ZERO reference to `customer_exclude` in their `conditional_run` formula, gating only on email regex + persona_key. 4 real current-customer rows (customer_exclude="TRUE") have a populated Persona Key matching one of these ungated actions today: kevin_burbridge@bcbsil.com (Blue Cross IL/MT/NM/OK/TX, cc_ops), xiaoping.ding@hcsc.com and rolande_odeniyi@hcsc.com (HCSC, coo_finance), angela_martinez@hcsc.com (HCSC, stars_quality). The dead-code safe-cast helper `customer_exclude_bool` (`f_0tigv0bPYTxSt3Zdh7s`) is wired into nothing. `send_ready` (`f_0thtsyrabg7qGSqe5gf`) also has zero reference to `customer_exclude` or `human_approved` despite its own formula_prompt claiming otherwise; these rows read HOLD today only because unrelated audit fields haven't run yet, not because a gate is blocking them.

**Secondary Stars finding (not yet independently verified, from the discovery pass):** the Contacts table's own hardcoded `customer_exclude` formula (allowlist humana/uhc/cvs/molina/elevance/hcsc) diverges from the shared Accounts (Master) table's (`t_0thuumoUcu6wAAhovti`) `customer_flag` column, which adds kaiser and scan. The two exclusion lists are not identical, worth reconciling.

**CONFIRMED LEAK 2 — WFM-Adjacency, table `t_0tic8arWbZp8bSx87Ad` ("L3").** `Send Ready` (`f_0ti9ygfsJv3y8g6Nkcz`) formula checks only `Final Audit Verdict` + `Final Voice Audit`, no reference anywhere to `customer_flag`/`New Logo Eligible`/`intent_status`. A per-row "Invoke Workflow" action (`f_0tieeexepsCroV9MtBk`) does pull `customer_flag` and feeds it to workflow `wf_0tie30io3hiPqSzVRU2`, but its output is consumed by nothing else in the table, an orphaned check. Live state: 518 HOLD / 6 READY across 524 rows (up from the registry's stale "0 rows" record, real rows have since loaded). The 6 READY rows (5 Elevance Health, 1 VNS Health) cross-check as `customer_flag="FALSE"` against the shared seed table (`t_0tict25TSXgTgdJgtZZ`) today, so no currently-flagged customer has breached yet, but the gate itself never consumes the flag. Molina, Centene, Point32Health, CareFirst, Blue Shield of CA, and Carelon are all present in this same 524-row table; if any of their domains flips to `customer_flag="TRUE"` on a future refresh, Send Ready would still flip to READY the moment copy audits pass.

**FLAGGED, NOT A LEAK — Cost-Mandate, table `t_0ti8tdqQAXiWMkx76Jj`.** `customer_exclude` is a real boolean here (not text), correctly consumed by `send_ready` (`!{{customer_exclude}}`), no leak. But the `Draft Audit` figure-integrity critic (`f_0ti9hp0WEN6VU2hVWsG`) hardcodes `disclosed_figure`, `disclosed_figure_source`, and `product_angle` as the literal string `"(none)"` for every row instead of pulling from Universe Lookup, the same bug CLASS as the historical `install_base` hardcode. Currently fails closed (msg1_critic Status = FAIL on all 7 rows, blocks every send), so it's a broken gate, not an active leak, but would misbehave the moment a row legitimately has a disclosed figure to check.

**UNVERIFIED — Back Office, table `t_0tingaqoNzymfmSpEZh`.** This table (313 rows, upstream contact sourcing/dedup) has no `customer_exclude`, `fo_risk_flag`, or `owner_cleared` column at all. Docs describe the real gate as an account-grain lookup from a separate BO universe table whose live id could not be located/confirmed. Treat any Back Office send as unsafe until that lookup is confirmed present and live-verified on the actual downstream send-readiness table (not this contacts table).

**VERDICT: STOP-THE-LINE.** Do not run or approve a send wave on Stars or WFM-Adjacency until the 3 ungated Stars sync actions and the WFM-Adjacency Send Ready formula are wired to their exclusion fields and re-validated on real rows. These are Clay UI column-formula edits (not agent-buildable, table/column structure is a UI-only surface per [[clay-golden-standard-and-motion-runbook]]'s capability boundary).

**Own-workflow bug found and fixed same day:** the script's reduce logic only bucketed `leak_found=true` (→verify) and `verdict==='PASS'` (→passed) and `verdict==='UNVERIFIED'`, so Cost-Mandate's real `verdict='FLAG', leak_found=false` result silently matched no bucket and was missing from the final report. Fixed same day by adding a `flaggedNonLeak` bucket plus an exhaustive `uncategorized` catch-all that logs a warning if anything still falls through. Lesson: any reduce step bucketing agent verdicts needs to be checked for exhaustiveness, not just the happy-path cases you designed for.
