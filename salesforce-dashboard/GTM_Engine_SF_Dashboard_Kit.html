GTM Engine · Salesforce reporting layer · v1 · Jul 15 2026

The dashboard the room was promised, and exactly how to build it

One Salesforce dashboard, open any time, that answers John's question from the thread: what do we expect, and how do we measure it. Engine results only, sourced never blended, shaped for pipeline council and the H1/H2 reviews. This kit is sequenced so the parts that need nothing from anyone ship first, and the parts waiting on the Salesforce seat are a 60-minute build the day it lands.

1 · The metrics contract

Everything on the dashboard traces to a line the execs have already read or heard. Nothing else earns a component.

MetricDefinitionAgainst
Sends + deliverabilitySends and bounces by persona lane; plain text, no opens (by design, never promise them)Warmup health
RepliesAny human reply; auto-replies and polite declines stay hereRange 6–11 on the full 143
Qualified conversationsA target persona engaging on the problemRange 3–7
Meetings to salesMeeting booked and handed to the owning sellerRange 2–4
Cost per qualified replyMotion credits ÷ qualified conversations, shown in credits AND dollars (~7¢/credit)Trend, no target
Engine-sourced pipelineOpportunities whose primary campaign source is an engine campaign; estimated never blends with realizedSourced vs realized, separate
The never-blend rule is structural: every report in this folder filters to engine campaigns or Lead Source = Clay. Engine numbers appear in council views as their own line, never summed into existing-motion totals.

2 · How data flows (system of action → system of record)

Clay runs the motion; Salesforce records what the business keeps: people touched, conversations, meetings, pipeline. The bridge is deliberately thin at Wave 1 scale (53 leads) and upgrades without rework.

PhaseBridgeEffort
v1 · launch weekWeekly CSV from Clay Contacts (name, email, company, persona, reply_status, sourced date) → Campaign Member import with statuses. At 53 rows this is minutes, and it makes the dashboard live before any integration exists.~15 min/wk
v2 · post-launchClay HTTP/webhook column updates the Campaign Member status the moment reply_status changes in Contacts. One column, fires on status change only.One build session
v3 · with AI EnablementThe data hub that already feeds Salesforce data INTO the engine carries engine results back. Jason's team owns the pipe; the dashboard doesn't change, only its feed does.Their roadmap

3 · Salesforce configuration (the Sierra list)

Everything here is standard objects, no packages, no code. Items marked Sierra are hers or need her admin hand; the rest is yours the day the seat lands.

Campaigns · 3 records

  • GTM Engine · Stars QBP Wave 1 · Persona 1 (Stars/Quality)
  • GTM Engine · Stars QBP Wave 1 · Persona 2 (Finance)
  • GTM Engine · Stars QBP Wave 1B · Longer-Horizon

Type = Email, Status = In Progress on launch. The GTM Engine · prefix is the name-based filter every report keys on (the foundational template's rule: filter on names, never IDs, so nothing breaks across sandboxes).

Campaign Member statuses Sierra

Staged → Sent → Replied → Qualified → Meeting Booked, plus Disqualified. "Responded" flag on Replied and above. Statuses only move forward, mirroring reply_status in Clay.

Fields

  • Lead Source picklist value "Clay" Sierra — her existing prep ticket; the one blocking dependency.
  • GTM_Motion__c picklist on Lead/Contact: star_ratings, back_office, cost_mandate, install_base, competitive — one field makes every future motion reportable with zero new build.
  • Engine_Sourced_Date__c date — mirrors the sourced_date stamp Clay sets at creation.

Cost feed (smallest thing that works)

A tiny custom object GTM_Spend__c: week, motion, credits used, dollar equivalent (credits × $0.0694), qualified-to-date. One record per week from the credit ledger, two minutes to enter, and cost per qualified reply becomes a real report instead of a slide claim. If object creation is locked down, phase-2 it and carry cost as a dashboard rich-text component updated weekly from the ledger.

5 · Dashboard layout (see the mockup file)

Lightning dashboard "GTM Engine · Star Ratings", 12-column layout, running user Dallas (dynamic later if council wants per-role visibility).

  • Row 1 · five metric components: Sends, Replies, Qualified, Meetings, Cost per qualified reply. Replies/Qualified/Meetings use gauge components with segment breakpoints set to the planning ranges (6–11 / 3–7 / 2–4), so "actuals against the ranges" is literally visible, not a caption.
  • Row 2 · funnel by persona: horizontal bar from R1, one color per lane, direct labels on.
  • Row 3 · engine-sourced pipeline (R5) + meetings table (R4): sourced sits alone; a text note names where existing-motion numbers live so no one asks why they aren't here.
  • Row 4 · spend: weekly credits line + cost per qualified reply, denominated in credits with the dollar equivalent beside it (~7¢ a credit, the $5,000 / 72,000 plan math).
  • Footer text component: "Engine-sourced only, never blended with existing motion. Opens not tracked by design. Estimates labeled." Plus a data-as-of stamp.

"Open any time," honestly stated: the reports behind every component are always live; the dashboard surface refreshes on the Refresh click (Unlimited-edition auto-refresh subscriptions can be added, pointed at the council, not at inboxes).
