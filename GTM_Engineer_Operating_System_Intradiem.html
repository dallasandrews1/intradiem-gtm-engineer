The Thesis

What a GTM Engineer actually does

Every B2B GTM org has the same shape: Salesforce is the database, Slack is where reps actually live, and a layer of point tools sits in between. What's almost always missing is the middleware — the thing that reads what happened, structures it, routes it to the right people, and writes it back to the CRM without a human retyping anything.

A GTM Engineer finds that missing layer, proves the gap is real, and closes it — fast, with the tools already in the building, before asking for new budget.

The architectural conviction

Salesforce is the system of record. Slack is the interface. AI is the middleware that reads from one and writes to the other — so a rep has near-zero reason to open Salesforce during their day.

The Operating Loop

Seven moves, every build, in order

1
Diagnose before you build

Audit what exists before writing a line of code. Most failures are "built on broken data" failures. Three layers: the connection (is SF↔Slack wired and user-mapped?), the object (do the fields the AI writes to exist?), the data (deduped contacts, correct emails, populated roles?).

2
Find the missing middleware

Name the manual gap out loud. The pattern: a tool posts intelligence into Slack, humans read it, then retype it into Salesforce — or skip it, so the CRM rots. Three quick questions and you've located the build.

3
Lock the foundation

Before tooling, write down how the org's data is interpreted: record types, the revenue source-of-truth field, the real stage list, the hygiene risks. A persistent Foundational Rules file every AI session loads — so every tool shares one definition of "correct."

4
Architect in four layers

Decompose every build into Capture → Intelligence → Distribution → Write-back, then map each to a tool that exists or a thin piece you build. The layering is the portable part — the vendor never matters.

5
Engineer the intelligence

The "magic" is a prompt, not a model. Context-enriched (transcript + SF object context, not one-pass) and stage-aware (a different schema-enforced prompt per pipeline stage). Short and actionable beats a wall of text.

6
Close the loop

Most DIY builds stop at "posted to Slack." Don't. The differentiator is the write-back — activity record, next-steps, contact intelligence, qualification fields — automatic or two-click. This is what makes Slack a headless front end for Salesforce.

7
Govern, enforce, roll out

A system that works Day 1 and rots by Day 90 is a failure. Validation rules, dedupe rules, monitoring for OAuth/token failures. Then roll out in order: connections first (the most-skipped, most-fatal step), clean data before launch, 30 days of tuning.

The Architecture Lens

Every intelligence build is the same four layers

LayerJobBuild with what's already there
1. CaptureGet a speaker-attributed transcript / signal somewhere readableExisting recorder, or any tool that outputs a transcript
2. IntelligenceTranscript + CRM context → structured outputClaude API + a stage-aware prompt
3. DistributionRoute the structured output to the right Slack channel(s)Slack API / webhook
4. Write-backPush the structured fields into SalesforceSF REST API, or a lightweight Slack→SF tool

The prompt is the product · Rule 1

Context-enriched, not one-pass. Feed the model the transcript plus the SF object context — stage, ARR, account, existing next steps. That's what produces source attribution and stage awareness instead of generic summary.

The prompt is the product · Rule 2

Stage-aware schema. A different extraction prompt per stage, each returning a defined JSON schema. A late-stage call focuses on legal/PO/signatures; an early call on pain + stakeholders.

Application

Day 1 → Week 1 at a Salesforce + Slack org

Day 1 · Access + Audit

Get SF read access; run discovery queries (record types, stages, owners, revenue field, custom fields). Confirm the SF↔Slack connector is live and my own user is mapped. Map the stack in writing and name the middleware gap publicly — a specific written artifact, not a verbal claim.

Days 2–3 · Foundation

Fill the Salesforce Foundational Rules file for this org. Audit the object layer (do next-steps / call-date / qualification fields exist? are Contact Roles enabled?). Run a contact email + duplicate audit on open-pipeline accounts.

Days 4–5 · First Proof

Stand up the smallest end-to-end slice that demonstrates the loop: capture → intelligence → Slack post → SF write-back, scoped to my own calls first. A live "call happened → Slack post → SF logged itself" demo beats any deck.

Throughout · Partner, don't lone-wolf

Find the RevOps/Salesforce admin and the Slack admin early — nothing routes or writes without them. Frame every build as closing a gap they already feel.

The Walk-In Kit

Day-1 diagnostic questions

Stack & Gap

  • What conversation tool are you using, and does it connect to SF or just Slack?
  • How do reps update Salesforce after a call — manual or automated?
  • Do managers read Slack or SF for deal intel?
  • Any Slack→SF automation running today?

Foundation

  • What fields are reps required to fill?
  • Is there a qualification framework with real SF fields behind it?
  • Deal-room channels in Slack + a naming convention?
  • Who owns the SF config and who owns Slack?

Hygiene & Access

  • Is SF↔Slack user-mapped cleanly by email/SAML?
  • Is API access enabled on the integration user?
  • Any security boundaries to respect (data-crossing, PII)?
  • Where do duplicates and free-text fields live?
Operating Beliefs

The principles underneath the method

  • The gap is the write-back, not the capture. Capturing intelligence is easy and already happening; getting it back into the system of record automatically is the unsolved part.
  • Ship the path of least resistance first. A Slack webhook ships in hours; a fully-approved CRM integration takes weeks. Get value flowing, then close the loop.
  • The prompt is the product. Stage-aware, context-enriched, schema-enforced. That's the leverage.
  • Consistency comes from a shared knowledge layer, not each tool's individual config. One Foundational Rules file beats five tools guessing.
  • Design for failure. Tokens expire, users get unmapped, data drifts. Monitoring and validation rules separate a demo from a system.
  • Adoption is an ordering problem. Connections first, clean data before launch, 30 days of tuning. Skip the order and the best architecture sits idle.
